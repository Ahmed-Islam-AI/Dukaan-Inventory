# Decisions

Settled calls and why. Do not silently reverse one: add a new entry that supersedes it.
All dated 2026-10-14 unless noted (initial planning: owner interview, CEO review, outside-voice review).

| # | Decision | Why |
|---|---|---|
| D-01 | Track both serial/IMEI units and plain quantities | Phones need per-unit identity (warranty, theft checks); accessories don't |
| D-02 | Generic for any shop type; onboarding sets the profile | Owner wants a Play Store product, not a one-off |
| D-03 | One phone now; sync-ready schema; SYNC_HANDOFF.md | Ship fast offline, avoid a rewrite when multi-device comes |
| D-04 | Receipts: PDF share (WhatsApp), Bluetooth thermal 58/80mm, A4 | Covers counter printers and WhatsApp-first customers |
| D-05 | Track cost, sale and profit | "Overall collection" is not enough to run a shop |
| D-06 | Play Store product, client first user, free v1 | Get feedback before monetising; billing hook later. No Play account yet |
| D-07 | Kotlin + Jetpack Compose + Room, single `:app` module | Best Bluetooth printer support, offline SQLite, fast |
| D-08 | PKR default, selectable currency, tax off by default, English + Urdu (RTL); receipt labels English | Pakistan market; most small shops aren't tax-registered |
| D-09 | v1 flows: sell, purchase, returns/void, customers + credit, expenses | Owner's selection |
| D-10 | v1 extras: camera scan, PIN/fingerprint lock, low stock, variants | Owner's selection |
| D-11 | Backup: Android Auto Backup of a snapshot file + manual export/import | Owner chose no Drive API work in v1. Risk: some OEMs disable Google backup → home reminder to export |
| D-12 | Working name "Dukaan", applicationId placeholder `app.dukaan.android`; personal project, not Moonlabor | Brand must not copy Vyapar. **applicationId is permanent after first Play upload** |
| D-13 | Sync-ready ledger: UUID ids, SyncMeta, soft delete, append-only stock_movement | Stock can be recomputed and merged; no conflicts on ledger rows |
| D-14 | Selling a QUANTITY item at 0 stock is allowed with a warning; SERIAL never | Blocking at the counter makes owners abandon the app |
| D-15 | FIFO cost for QUANTITY items; exact unit cost for SERIAL | Owner's choice (more precise than average cost) |
| D-16 | Sale with no lot → `pendingQty`, filled by the next purchase oldest-first | Profit corrects itself once the purchase is entered |
| D-17 | Sales are never deleted: void with reason. Purchases: void only if untouched, else stock adjustment | Collection must always be explainable; staff can't erase cash sales |
| D-18 | Invoice `A-0001`: per-device prefix in DataStore, next = MAX(seq)+1, no stored counter | No clashes with future devices; survives reinstall without resetting to 1 |
| D-19 | Firebase Crashlytics, crashes only, no business data | Can't fix crashes we can't see; privacy |
| D-20 | A sold/returned IMEI can be purchased again (buy-back/trade-in) | Mobile shops buy back used phones daily |
| D-21 | One Canvas receipt renderer → PDF, A4 and thermal raster | ESC/POS text mode can't print Urdu names |
| D-22 | Returns: discount/tax split pro-rata; refund reduces customer credit first, cash for the excess | Totals and balances stay consistent |
| D-23 | Manual DI (`AppContainer`) instead of Hilt | Superseded plan's "Hilt": ~10 ViewModels over one DB don't need it; no KSP round for DI; same pattern already proven in owner's gym_fit project. Revisit past ~15 ViewModels |
| D-24 | Room 3 (`androidx.room3`) and AGP 9 built-in Kotlin | Version set already verified on the dev machine |
| D-25 | No SQL foreign keys; integrity via LedgerService + invariant tests | Synced rows can arrive out of order |
| D-26 | `allowBackup=false` until M2 backup rules exist | Backing up the live WAL database can restore a corrupt copy |
| D-27 | Soft delete only for master data (category, product, variant, party); ledger tables never deleted. Purchase void → lots qtyRemaining 0, serials VOIDED | 2026-10-15 eng review: one rule means no forgotten `deletedAt` filter feeding a voided lot into FIFO |
| D-28 | Backup snapshot: VACUUM INTO tmp → integrity_check → atomic rename | 2026-10-15 eng review: a kill mid-write must never leave a corrupt restore point |
| D-29 | Collection = payments IN − OUT by payment date; Sales/Profit/Receivable defined in ARCHITECTURE.md | 2026-10-15 eng review: credit sales must not inflate the cash-drawer number |
| D-30 | Money input accepts Urdu/Arabic digits | 2026-10-15 eng review: Urdu keyboards type ۱۲۳ |
| D-31 | Seeded randomized invariant test (≈500 random ops) in M2 | 2026-10-15 eng review: catches FIFO/pending/void/return ordering bugs |
| D-32 | Ship bundled SQLite (`BundledSQLiteDriver`) in production | 2026-10-15 eng review (outside voice): Android 8-10 system SQLite lacks VACUUM INTO; tests and phones now run the same SQLite. Cost ~1-2 MB per ABI |
| D-33 | IMEI buy-back inserts a NEW serial_unit row; old row stays SOLD | Reactivating overwrote cost/history and let a later void double-count stock |
| D-34 | Lots have a source (PURCHASE/OPENING/ADJUSTMENT/RETURN); `lot_allocation` (sale lines and −adjustments) replaces sale_line_lot, with reversedQtyMilli | Opening stock and adjustments had no lot, breaking FIFO cost and invariant 2 |
| D-35 | `serial_unit.liveSerial` + plain unique index instead of a raw partial index | A raw-SQL index fails Room's migration schema validation |
| D-36 | `businessDay` (yyyyMMdd in shop timeZone) stored at write; `voidedAt` on voidable docs; FIFO tie-break (receivedAt, createdAt, id) | Reports must not shift with timezone/clock; closed days never change |
| D-37 | Discount before tax, invoice-level; taxRateBp snapshot on sale; cumulative rounding for partial returns | Partial refunds always sum to the exact line net |
| D-38 | `payment.kind` + unique `reversesPaymentId`; sale_return has status and can be voided | No double reversal; a wrong return no longer makes its sale unfixable |
| D-39 | Quantities are Long milli-units (`...Milli`, `Qty`); per-item allowDecimalQty | Generic shops sell 2.5 kg / 1.5 m; decided before the M2 schema freeze |
| D-40 | Home hero number = Collection (cash received), with cash/bank/wallet split; Sales/Profit/Bills in a strip below | 2026-10-15 design review: matches the cash drawer at day end |
| D-41 | Typeface IBM Plex Sans (bundled) + Noto Nastaliq Urdu + IBM Plex Mono for IMEIs; not Inter | Inter reads as the generic default; Plex has clear tabular numerals; bundling keeps every phone brand identical |
| D-42 | Lakh grouping (1,26,400) for PKR/INR/BDT/NPR; western grouping otherwise | How Pakistani shopkeepers read amounts |
| D-43 | Currency symbol only on totals, hero numbers, pay sheet, receipts; not on cart lines/lists | Less noise when scanning lists |
| D-44 | Latin digits in the Urdu UI | Matches receipts, banks and other Pakistani apps |
| D-45 | "Hide cost & profit" eye toggle on Home/Items; re-show needs PIN (M6) | Cost/profit visible to anyone holding the phone until staff accounts exist |
| D-46 | Auto-print after Charge when a thermal printer is paired; receipt screen still offers share/reprint | Saves a tap on every sale |
| D-47 | Device-local settings (deviceId, invoice prefix, hide cost) in SharedPreferences, not DataStore | 2026-10-15 M1: three small values; SharedPreferences is built in, synchronous, and excluded from backup by default, so a restore gets a fresh deviceId (D-18) for free |
| D-48 | IBM Plex Sans bundled as the variable font file (wdth,wght) via Compose FontVariation | Google Fonts now ships Plex Sans only as a variable font; one 0.5 MB file covers all weights |
| D-49 | Category entry is free text with case-insensitive find-or-create | No dropdown widget needed; duplicates like "chargers"/"Chargers" are still prevented |
| D-50 | The Sell cart's ViewModel is scoped to the activity, not the nav entry | 2026-10-15 M2 device test: Back from Sell discarded a cart in progress; a shopkeeper stepping away mid-sale must not lose it |
| D-51 | Receipts render at 80 mm width (576 px) for the PDF; A4 prints that image at 60% page width, sliced across pages | One renderer for every output (D-21); readable on A4 without a separate layout |
| D-52 | Auto-print after Charge (D-46) ships with the Bluetooth thermal printer in M3 | Nothing to auto-print to until a thermal printer is paired; A4 print is a deliberate action |
| D-53 | Import keeps the previous database as `dukaan.db.before-import` and restarts the process | A wrong restore can be undone by support; restart guarantees no screen keeps the old database open |
| D-54 | Number dialogs (price, qty, discount, prefix) open focused with the value selected | M2 device test: typing 2000 over a leftover 0 produced 20000 |
| D-55 | Bottom bar shows only built tabs; Home and Parties appear when M4/M5 ship (done: all five tabs live since 0.6.0) | 2026-10-15 design review: the client uses the app now and must not see "arrives in M5" |
| D-56 | Thermal printing via our own ESC/POS raster encoder over Bluetooth SPP, not the DantSu library | 2026-10-15 M3: ~100 lines, unit-tested, no JitPack dependency; raster works on virtually all 58/80 mm printers and prints Urdu (D-21) |
| D-58 | Voiding a return re-takes its QUANTITY stock FIFO at today's lots (pending if none), not "the same lots" | 2026-10-15 M4: the frozen schema doesn't record which allocations a return reversed, and those lots may be resold by then. Invariants hold; only cost can differ if lot prices changed in between |
| D-59 | Expenses may be soft-deleted (deletedAt) | 2026-10-15 M4: an expense touches no stock and no payment, so deleting a typo loses no ledger history; M5 reports filter deletedAt |
| D-60 | Return refunds (payment kind REFUND) link to the return, not the sale; a sale line's costPaisa is always net of returns | 2026-10-15 M4: the receipt's "Paid" stays what was paid at the counter; gross profit = Σ ACTIVE line cost, no double subtraction of costReversedPaisa (kept for per-day reports) |
| D-61 | Sales/profit by day: a voided bill drops out of its sale day entirely; returns subtract refund and cost on the return day; cost per sale day = line cost + cost later reversed by returns. Money in − out keeps reversals on the void day | 2026-10-15 M5: voidedAt has no stored businessDay and a voided QUANTITY line's original cost is gone (allocations reversed). A void corrects a mistake; the cash given back still shows on the day it happened |
| D-62 | App lock settings (PIN hash, salt, failures, lock-after, language) in device SharedPreferences, not DataStore | 2026-10-15 M6: same reasoning as D-47; never backed up, so a restored phone sets its own PIN. Forgotten PIN = phone screen lock via BiometricPrompt (BIOMETRIC_WEAK or DEVICE_CREDENTIAL) |
| D-63 | Lock again after 5 minutes in the background by default (0/1/5/15 selectable) | Sharing a receipt to WhatsApp sends the app to the background; locking on every share would be maddening |
| D-64 | androidx.biometric 1.1.0 (last stable) | 1.2+ exist only as alphas; the pinned 1.4.0 never shipped |
| D-65 | Language picker restarts the process; App Bundle language splits disabled | ViewModels format messages with the app context, which must switch too; Play would otherwise not install Urdu on an English phone |
| D-66 | Crashlytics plugins and SDK applied only when app/google-services.json exists | The app builds, tests and ships without Firebase or INTERNET until the owner creates a project; no PII ever (D-19) |
| D-67 | Icon-first UI: icon badges on every row and action, picture tiles for actions (Home quick actions, receipt, party, item), white cards on a tinted page, one-line labels; replaces "divider rows, not cards" | 2026-10-15 owner review: too text-heavy for non-technical shopkeepers; the Vyapar reference is self-explanatory through icons. Material Icons as vector drawables (no icon library, keeps the no-dependency rule) |
| D-68 | Every save/void confirms with a short pill at the TOP of the screen; Home money card on a saffron gradient; forms grouped in titled cards; "Sale saved" banner after Charge; Sell header shows the next bill number | 2026-10-15 owner: "more professional and user friendly". Silent saves left shopkeepers unsure; a bottom pill covered Save and floating Add buttons |
| D-69 | Motion: 150-600 ms ease-out; screens fade + settle from 97% (direction-free, so RTL needs nothing); press dips to 96%; money counts up with Long maths; list items animate placement | 2026-10-15 owner: "add proper animation". Calm motion reads professional; never delays a tap |
| D-70 | Accounts on Firebase Spark (free): Auth (Google, email + password, phone + password) + Firestore. SMS code login waits for Blaze. Phone + password = Firebase email account (real email if given, else a hidden one) + `phoneLogins/{digits}` lookup | 2026-10-15 owner Q&A: control who uses the app, keep data safe, several phones; free first. Trade-offs accepted: number not proven by SMS; lookup reveals the login email for a known number |
| D-71 | Phase 1 cloud copy = the WAL-safe snapshot, gzipped, in Firestore document chunks (< 1 MiB each, sha256-checked), restored through the import path | Cloud Storage needs Blaze for new projects; row-level sync is Phase 3 |
| D-72 | The account check blocks (and wipes) only on explicit signals (user disabled/deleted, shop status blocked); everything else is offline grace (14 days). Firestore cache memory-only | 2026-10-15 emulator test: an ambiguous error right after a restore wiped the phone. A wrong block destroys a shop's data on the phone; a missed block costs nothing until the next check |
| D-73 | Staff join by invite: `invites/{lower-case email or phone digits}` written by the owner, accepted by the person whose account matches the key. The client never reads an invite before writing it; a refused write means "already invited" | 2026-10-15 Phase 2 test: a pre-read of an invite that doesn't exist is refused by the rules (no one may see another person's invite). Owner sign-up rule uses `getAfter(shop)` so shop + owner doc go in one batch |
| D-74 | ~~Until live sync, each staff member uploads their own cloud copy~~ superseded by D-79. Backup & restore stays owner-only | A staff upload over the shop's copy would erase the owner's sales |
| D-75 | Stock is derived from facts by one replay (`StockReplay`): lots, allocations, line cost/pending, return cost, IMEI status, onHand. LedgerService writes facts and calls it; sync calls it after a merge. Returns/voids set a target the line settles to. `updatedAt` changes only with facts. lot_allocation became derived (rebuilt, not ledger) | 2026-10-15 Phase 3: two phones consuming the same lot offline can't both be right; recomputing from merged facts makes every phone agree (SYNC_HANDOFF option "authority" needed a server; weighted average reversed D-15). One FIFO implementation instead of two. Existing tests pass unchanged |
| D-76 | Rows the same action creates on two phones get ids from their meaning (void movements, reversals, IMEI events, parties/categories by name) | A bill voided on two phones offline must count once; "Ali" typed on two phones is one customer |
| D-77 | Sync = append-only change log in Firestore, one gzipped document per push (rows from a trigger-filled outbox), applied in server-time order, newest `updatedAt` wins per row. Bill prefix unique per phone; (prefix, number) index no longer unique. Schema v2 (outbox, sync state) | Spark limits: per-row documents would cost 6-8 writes per sale; one document per push costs 1. Triggers catch every writer. A unique index would block a merge forever on a prefix clash |
| D-78 | Conflicts are kept and listed for the owner ("Problems between phones"), never auto-resolved | Owner decision (Q&A): same IMEI sold on two phones → keep both bills and flag. Only the shop knows which bill is real |
| D-79 | Every phone starts from the shop's cloud copy (owner keeps it fresh) and live sync brings the rest; staff copies retired. Log out pushes every change first | With sync, a staff copy is redundant; the copy only saves a new phone from reading the whole change log |
| D-80 | Invoice templates: A4 invoice (Modern / Classic / Minimal) drawn as vector PDF pages for Share and A4; slip (Classic / Compact / Bold) for the thermal printer. Design (templates, brand colour, logo as a small base64 PNG, tax number, terms, footer) lives on the shop row (schema v3) and is owner-only | 2026-10-15 owner: "the invoice print is very simple; add templates the user can customize". A slip scaled to A4 looked like a till roll; one design per shop keeps every phone's invoices alike and syncs with the row |
| D-81 | ~~Sign-up on a phone that already holds a shop asks: keep its data (the shop row takes the typed details) or start a new, empty shop (confirmed, then the phone's tables are cleared after the account exists) | 2026-10-15 owner: an email sign-up silently became "Ali Mobiles". Adopting local data is right for the client but must never be a surprise~~ superseded by D-82 |
| D-82 | A new account is always a new, empty shop: sign-up clears the phone's shop data (tables, snapshot, cached receipts) once the account exists. Welcome offers "Save a backup file first" when a shop is on the phone; existing data reaches an account by importing that file (More → Backup) | 2026-10-15 owner: "user can create as many accounts as he wants; a new account removes the existing company data" (reverses D-81 and Phase 1's "upload existing data"). Welcome's backup button was removed at the owner's request (2026-10-15); pre-account data must be exported from More → Backup before the app is updated to accounts |
| D-83 | Home: greeting header, money card with sliding period switch + payment pills + margin, "Last 7 days" bar chart (sales − refunds per shop day), staggered entrance (`Reveal`, once per app visit), whole-rupee count-up | 2026-10-15 owner: "refine the home screen, more professional and animated". The week shape is the most-asked question after "how much today"; motion stays short (≤ 0.6 s) and never delays a tap |
| D-84 | Signed-out look: saffron launch window (themes.xml, Android 12 splash attributes) handing over to a landing carousel (4 features, auto-advance 3.8 s, floating illustration) and saffron headers with forms on an overlapping white sheet; sliding Phone / Email switch; sign-up steps shown | 2026-10-15 owner: "make login and sign up more professional, new look; a landing page as the first page". One brand surface from launch to form; no new dependency (Pager is in Compose Foundation) |
| D-85 | Category required (none = "Other"); variant keeps a usual purchase price (default for Add stock, newest purchase cost replaces it; profit still from FIFO batch cost); Sell and Add stock pick through a category → item sheet (`PickDao`); barcode is the main code, per-unit serial tracking optional; serial label "IMEI" only for shopType mobiles. Schema v4 | 2026-10-16 owner: generic shops, not only mobiles; "two prices to check sale and profit"; "select category then item to sell". Owner Q&A: required category, editable default price, add to cart and keep picking, barcode + optional serial, same picker for stock |
| D-86 | Design pass: clean light screens with saffron for actions (filled Add buttons), bold page titles, letter tiles coloured by category, category chips on Items, one-row date chips on Reports. Landing/login/sign-up untouched | 2026-10-16 owner: "professional and new look… landing, login and register are good, don't change" |
| D-57 | Scanned codes pass through `ScanCodes.clean` (strip IMEI labels/spaces, Luhn check); scanner returns results to the asking field via navigation | Box labels often read "IMEI:3567…"; a Luhn-valid 15-digit run is the IMEI, other codes pass unchanged |
